Who can sign Alcove, and how.

Alcove starts with Windows and takes over the desktop. A signature on it is a claim that the thing you are about to run is the thing we built, from the source you can read. This page says who is allowed to make that claim, where the keys that make it live, and what we will not put our name on. It exists because we ask you to trust a signature, and a signature nobody explains is just a checkbox.

Where this stands today: Alcove is not Authenticode-signed. An application for a free certificate under an open-source signing programme is pending, and it may well be refused — in which case this page says so and Alcove stays unsigned until another route turns up. The policy below governs signing whenever it happens, not a certificate we already hold. Nothing here describes a protection you have today.

01 Roles A short list

One maintainer, and we'd rather say so.

Alcove is written by one person in their own time. Pretending otherwise would be the first dishonest thing on this page. So the roles below are held by the same human, and the separation that a larger project gets from having several pairs of eyes, this one gets from building in public, on a public pipeline, from public source.

Signing roles for Alcove releases
RoleWho, and what they may do
AuthorThe maintainer. Writes the code and pushes the version tag that starts a release build.
ReviewerThe maintainer. Checks the built installer against the tag it claims to come from before anything is published.
ApproverThe maintainer. The only person who may approve a signing request or publish a release.

Should anyone else ever gain the ability to approve a signing request, this page changes on the same day, and the change is in the site's git history where you can see it. Multi-factor authentication is required on the source repository for every one of those roles, and on the signing service once there is one to require it on.

02 Keys Two of them

Where the keys live.

Alcove carries two separate signatures, and they answer different questions. Neither key is in the repository, and neither is on a build machine we don't control.

Key 1

The update key

A minisign key that signs every update artifact. Alcove refuses an update that doesn't verify against the public half, which is printed in tauri.conf.json for you to check. The private half is held offline by the maintainer, has never been in the repository, and cannot be regenerated: if it were lost, existing installs would simply stop accepting updates rather than start accepting the wrong ones.

Key 2

The Windows signature

Authenticode, the one that decides what the UAC dialog says about the publisher. Alcove is not Authenticode-signed, and the download page says so plainly rather than letting Windows break the news. If the pending application succeeds, the certificate and the publisher name it shows are documented here before the first signed build ships. If it doesn't, this paragraph stays as it is.

Version 0.2.3 was built on the maintainer's machine and published by hand, and its SHA-256 sits beside the download so you can check you got what we uploaded. From the next release that moves to GitHub Actions, building from a tagged commit with an attestation you can verify against this repository. Until you see that attestation on a release, assume the older method.

03 Scope Ours only

What we will and won't sign.

Will

Our own builds, our own source

Only binaries built by our own pipeline from our own repository, at a commit that exists in public history. Nothing gets signed on request, on behalf of anyone else, or because it arrived by email.

Won't

Anything that attacks a machine

No hacking tools, no code whose purpose is exploiting a vulnerability, no bundled adware, no third-party payload riding along with the installer. Alcove ships Alcove.

Won't

Anything we can't read

No obfuscated or closed components. Every part of what we sign is MIT and readable, apart from the platform libraries Windows itself provides.

04 Privacy Nothing to report

What the signed build does to your machine.

A signature says who built it. It doesn't say what the thing does, so here is that too.

Data

None leaves

No account, no telemetry, no analytics, no crash reporting. Alcove works with the network unplugged. The only question it ever asks the internet is whether a newer build exists, and you can see that request in the source. Your layout lives in one file on your own disk, at %APPDATA%\com.alcove.desktop\desktop.json.

Removal

It leaves when you tell it to

The installer runs as the current user, needs no admin rights, and uninstalls from Windows' own Apps list. Uninstalling removes the sign-in entry with it. Ctrl+Shift+F12 hands the desktop back to Explorer at any moment, without uninstalling anything.

05 Reporting Tell us

If you find a signed build that shouldn't exist.

A signed installer that we didn't publish, a signature that doesn't verify, a download mirror we've never heard of: mail hello@cromis.org and say what you saw and where. We will help investigate any misuse of a certificate that carries our name, and we would rather hear about it awkwardly than not at all. Official builds come from the releases page and nowhere else.
