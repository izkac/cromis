DOC. 003  ForgeKit / what it is, and how it works Rev. 2026  ·  Version 0.3.54

Make the agent finish the job.

A coding agent will happily tell you it's done. ForgeKit installs the skills that make it prove it. Forge turns a feature request into a tracked change with a gate at every phase, and thorough code review is a review pipeline you invoke on purpose. The gates are mechanical rather than polite. A session can't reach done while a test is still stubbed, a capability was never wired up, or acceptance was never actually executed. Hasn't your project got a harness to run that acceptance against? Then Forge will sit down and build one with you. And what a session learns outlives it: a findings ledger that belongs to the project, plus one table showing every session running anywhere on the machine.

01 What it does Four things

It's a pipeline, and you have to ask for it.

Forge never starts on its own. You ask for it by name, and from that moment the work has phases, artefacts, and a gate waiting at the end of each one.

1.1

Seven phases, each leaving something behind

Your request becomes a tracked change: a proposal, a design, a task list, and a plain-language operator brief that's the bit you'll actually read. Implementation runs one subagent per task group, test first, with a review at every group boundary. Nothing moves forward on somebody's word for it. Each phase transition is a command, and it's allowed to say no.

1.2

It argues against its own ceremony

Most work doesn't need a pipeline, and the tooling cheerfully agrees. Triage waves a rename or a question straight through. Even halfway into a session, a plan that turns out small enough trips an exit ramp, and the agent will offer to leave Forge before it scaffolds a single spec. A high-risk change gets no such offer, however small it looks.

1.3

Gates that count things

Claim a capability and it has to show up in the spine matrix with real runtime behind it. Acceptance means an executed command with a recorded hash. A nicely worded paragraph claiming it passed won't do. Wiring you've left for later goes into the deferral registry and stays visible there. Then forge integrity-check runs at the close and refuses a session that faked any of it.

1.4

It builds the rig it will be judged on

Executed acceptance needs something to execute against, so Forge goes and builds one. /forge:harness explores the project and proposes what to boot, what a probe through the real product looks like, and what a fresh checkout has to install first. Then it waits for you to approve it, because a harness is committed infrastructure rather than session scratch. Once it's proven it gets recorded, and every later session reuses it instead of asking you all over again.

Those recorded prerequisites matter more than they look. A probe that only ever went green inside the agent's own sandbox isn't proven at all. It's the failure you'll hit on your first real run. Forge never detects a tool and never installs one. It records what was needed, and when a loop later goes red, that's the first thing it tells you to suspect.

02 Across sessions Two registers that stick around

The work outlives the conversation.

A session ends and its chat window closes. Whatever it learned along the way shouldn't disappear with it, and whatever is running in the next window over shouldn't be a mystery to you.

2.1

Every session, every project, one table

Forge sessions register themselves, so forge fleet list shows you all of them at once, across projects and across editors, with phase, task count, health and age. watch is the live view. view <session> --transcript 20 tails what an agent is actually saying. send drops a message into a running session and it arrives on the next turn. Start two sessions in one project and both agents get a warning, so you can decide: carry on, split into a worktree, or pause one.

forge fleet report is that same data read as a trend: grades, review depth, and how often a gate had to be capped.

2.2

A ledger you'll actually come back to

Everything spotted in passing and out of scope gets filed the day it's seen, with a kind, a severity and an id. The bug in the next module over. The shortcut somebody took on purpose. The idea worth trying one day. Findings can depend on other findings, be resolved with a note, or reopened against the id that got closed a bit too early.

The ledger belongs to the project rather than the session. Escape hatches taken at a gate land there too, so a waiver stays visible long after the conversation that granted it is gone. forge cleanup prunes finished session scratch and leaves the ledgers standing.

03 Good behaviour Playing nicely

It sits beside your agent and stays out of the way.

ForgeKit is a handful of files on your disk and a CLI on your PATH. There's no service sitting in the middle and nothing to sign up for.

  • Your agent, unchanged. Claude Code, Cursor, Codex, GitHub Copilot, Gemini, Windsurf and opencode all read the same skill folder. Pick your harnesses at install, and running it again reconciles whatever changed.
  • Nothing runs unasked. Forge starts when you invoke it. Thorough code review never auto-loads at all. You ask for it by name, or it simply doesn't happen.
  • The planning engine is yours. Use the OpenSpec CLI if you've got it, or the built-in specs engine if you haven't. Both share the same change layout, so switching later doesn't move a single file.
  • Counts, and only counts. Session metrics get harvested afterwards from transcripts your agent had already written: model names, tool names, phases, timestamps, totals. Your prompts, the replies, command strings and file contents are never recorded.
  • Nothing is sent anywhere. Metrics land in a file inside your project. No endpoint, no key, no account. Telemetry that can't run degrades to unavailable and gets out of the way rather than blocking a phase on you.
  • Uninstalling is just a delete. forgekit uninstall removes the skill directories. What's left is your repository, exactly as your agent left it.

04 What gets installed The full list

Five skills, three commands.

The skills, and the CLIs that drive them
NameWhat it is
forgeThe workflow skill: triage, phases, gates, integrity, scorecard
thorough-code-reviewA review pipeline over a branch or a diff: signals, carryforward, merge, render
archive-to-adrTurns an archived change into an Architecture Decision Record
git-resolve-adr-conflictSettles the merge conflicts an ADR index tends to collect
plain-languageTakes the jargon out of whatever the agent writes back to you
forgekitThe installer: pick skills against agents, then list, update, uninstall
forge · reviewThe two day-to-day CLIs, same package

ADRs are optional and stay switched off until you ask for them. Turn them on and you get the two ADR skills, plus an index, a decisions file, and the hooks that speak up when a change gets archived without one.

05 Licence MIT

MIT. Free, and free to fork.

ForgeKit is MIT. It's published on npm, the source is on GitHub, and you're welcome to fork it and go. It's a developer tool, and honestly, a developer tool you aren't allowed to read is a hard thing to trust.

Credit where it's due. The Forge skill and several of its bundled workflows (brainstorming, TDD, subagent-driven development, verification before completion, systematic debugging) started life as Superpowers skills under MIT, and we adapted them into a maintained fork. You don't need Superpowers installed to run any of it. The planning engines, the ADR skills, the review pipeline and the CLI are ForgeKit's own work.

06 Install That's the lot

Version 0.3.54

Two commands and you're wired in.

The installer asks which skills you want, which harnesses, and which planning engine, then remembers your answers. Point it at a project and forge init writes the commands, rules and hooks for that repository.
